Проверены имена и заполненность переменных в переданных `server/opt/wirehouse/.env` и `runtime.env`. Первый содержит параметры релиза, БД/JWT, Telegram/VK, доставки OTP и путей файлов. Второй — первоначальные параметры развертывания, включая исходный пароль администратора, который не является доказательством текущего пароля.

Данные доступа не копировались в `.env` разработки, отчеты или Git. `.env.example` и deploy env example — шаблоны, не рабочие доступы. Параметров подключения адаптера 1С в переданных env нет. Рабочий сервер на момент проверки не содержит процессов 1С; установленная база найдена на этом компьютере.

В шаблонах теперь явно указана среда обмена: `test` для локальной разработки, `production` для сервера. Существующие рабочие env не менялись.

`npm audit --omit=dev` при обследовании обнаружил одно критическое предупреждение у `@capacitor/android`: [GHSA-rvm3-566m-v7fv](https://github.com/advisories/GHSA-rvm3-566m-v7fv). ## Целевой обмен

Для этой файловой базы выбран проектный путь: расширение БП с отдельными регистрами идентичностей, ЛС/помещений/приборов и входящих квитанций; исходящие HTTPS-запросы из 1С к CRM. Открывать файловую базу в интернет для такого обмена не требуется. Это решение плана, расширение пока не собрано и не установлено.

Основание: платформа поддерживает клиентские HTTP-запросы и стандартный REST/OData; OData требует публикации приложения и сам по себе не задает предметную модель обмена. [Документация 1С о REST](https://v8.1c.ru/platforma/rest-interfeys/). COM оставлен альтернативой для обследования после исправления регистрации: [внешнее соединение 1С](https://v8.1c.ru/platforma/vneshnee-soedinenie/).

Порядок зависимостей: объекты → помещения → контрагенты → договоры → ЛС → приборы → выписки. Для любого внешнего ID учитываются база, тип сущности и ID. Суммы не пересчитываются в CRM. Неполные связи попадают в журнал и исправляются явно, без подбора по похожему названию.

Со стороны 1С каждое входящее сообщение должно записывать результат и квитанцию `(sourceId,messageId,payloadHash)` атомарно. Повтор после потери HTTP ack возвращает ту же квитанцию без повторной бизнес-записи; другой payload с тем же ID отклоняется. Успешный ack CRM отправляется после COMMIT 1С. Несопоставленное показание нельзя подтверждать как доставленное.

Для файловой базы требуется проверенный механизм регулярного запуска при закрытом клиенте: отдельный агент/запланированный запуск либо переход к клиент-серверному режиму. Наличие фонового задания при открытом приложении не является круглосуточной автоматизацией.

## Первый результат в коде

Добавлены входящие `kind=properties` и `kind=units` в существующий endpoint обмена. Объекты создаются/обновляются по source-bound внешним ID, родитель помещения разрешается только в том же источнике. Импорт не меняет занятость, расположение на плане, документы или права. Неизвестные поля отклоняются. Автоматического совпадения по имени нет; существующие записи подключаются ручным mapping с версией 0.

Миграция `011-catalog-import.sql` сохраняет хеш подтвержденного снимка в `external_links.payload_hash`. Сравнение с ним позволяет не перетирать локальные уточнения при повторе той же версии. Одинаковая версия с другим содержимым отклоняется; старая пропускается. Смена родительского объекта и неоднозначный источник изменений запрещены. При отсутствии обязательных площадей/класса из БП их нужно явно определить в настройках соответствий, а не синтезировать фиктивные значения.

Исправлена обнаруженная PostgreSQL-регрессия атомарности: прежнее присваивание `db.data = before` в обработчике ошибки создавало затеняющее свойство на facade Proxy и не восстанавливало рабочую модель запроса. Теперь восстанавливаются коллекции текущего доменного объекта; журнал ошибки сохраняется, бизнес-строки пакета откатываются. Проверяется также последующий запрос в том же экземпляре API.

Новый `scripts/inspect-one-c.py` повторяемо экспортирует только корень метаданных или анализирует готовый XML; отчет остается в игнорируемой `.local`. Пример без подключения к базе:

```powershell
python scripts/inspect-one-c.py --configuration '..\.local\1c-metadata\config\Configuration.xml' --details '..\.local\1c-metadata\details' --output '.local\one-c'
```

Новые и измененные пути: `packages/contracts/src/accounting.ts`, `apps/api/src/domain/accounting.js`, `apps/api/src/persistence/{business-schema.js,migrate.js,migrations/011-catalog-import.sql}`, `tests/accounting-catalog.test.mjs`, `tests/postgres/accounting-catalog.test.mjs`, `scripts/inspect-one-c.py`, `.env.example`, `infra/deploy/server.env.example`, этот отчет и документация протокола.

# Готовность демонстрационных доступов и данных — 5 ноября 2026

Проверен только помеченный объект **«ТЕСТ WH-DEMO-20261028 Склад»** и его помещения DEMO-101/DEMO-102. Этот документ дополняет [карту процессов ролей](ROLE_PROCESS_ROADMAPS_RU.md) и [сверку ТЗ](SPEC_STATUS_RU.md): готовность конкретного набора данных отдельно от наличия механизма в программе.

## Договоры личных кабинетов

До подготовки у тестового арендатора DEMO-101 и совмещённого участника DEMO-102 был доступ к своему одному лицевому счёту, но список договоров был пуст. Причина установлена по действующему разграничению: назначение на конкретный ЛС не расширяется до финансового контекста договора; список договоров требует `finance.read` именно в допустимом контексте договора. Это не исправлялось выдачей прав на весь объект.

Через обычный административный API добавлены ровно два явных назначения `businessRole=tenant`, `scopeType=lease`: арендатору — договор DEMO-101, совмещённому участнику — договор DEMO-102. Набор семи разрешений, даты 01.01.2026–31.12.2027 и сохранение истории скопированы из соответствующего действующего назначения на ЛС. Перед созданием проверены имена тестовых пользователей, точные идентификаторы manifest, родительские связи и отсутствие эквивалентных действующих назначений. Старые назначения сохранены; роли, пароли, суммы, показания и состояния работ не менялись.

Повторное чтение API существующими сессиями подтвердило:

| Личный кабинет | Договоров | ЛС | Граница доступа |
|---|---:|---:|---|
| Арендатор DEMO-101 | 1 | 1 | Только договор и ЛС DEMO-101 |
| Собственник DEMO-101 + арендатор DEMO-102 | 1 | 1 | Договор и расчёты арендатора только DEMO-102; чужой ЛС DEMO-101 не виден |
| Исполнитель | — | 0 | Финансовые ЛС не выдавались |
| Участник без назначений | 0 | 0 | Объектов 0 |

Исходные снимки пустого списка договоров сохранены приватно. Новые снимки показывают фактический результат двух назначений. Запросы, ответы, UUID, состояние до/после и основание находятся в приватной папке `.local/demo-2026-11-05/role-preparation/`, без включения паролей и токенов в инструкцию.

## P1: ответственный за импортированный прибор

Сценарий **«исполнитель → передать показание» сейчас не подготовлен на этом тестовом наборе**: у импортированного прибора DEMO-101 `responsibleId=null`. Рабочие задания исполнителя доступны; отсутствие закреплённого прибора не отменяет их готовность. Показания для демонстрации обмена передаёт арендатор/совмещённый участник, затем проверяет инженер.

Найден конкретный программный пробел, который нужно устранить до приёмки устойчивого закрепления импортированных приборов:

- [Входной контракт прибора 1С](../../packages/contracts/src/accounting.ts#L137) не содержит `responsibleId`: это операционная настройка сайта.
- [Обработчик импорта](../../apps/api/src/domain/accounting.js#L468) явно добавляет `responsibleId: null` перед обновлением прибора.
- [Сохранение операции](../../apps/api/src/operations.js#L333) объединяет старую запись с входным телом, поэтому явно переданный `null` заменяет ранее назначенного сотрудника. [Сохранение поля](../../apps/api/src/operations.js#L620) записывает это значение.
- [Форма исполнителя](../../apps/web/src/features/business/ReadingsWorkspace.tsx#L164) отбирает активные приборы по `responsibleId === workerId`.

Сброс произойдёт **при применении более новой принятой версии этого прибора из 1С**, а не от простого обновления страницы или повторного неизменённого пакета: [старые/равные версии пропускаются](../../apps/api/src/domain/accounting.js#L389). Поэтому временно назначать сотрудника только ради непустого скриншота не стали. Прибор не изменяли, импорт и регламент не останавливали, новые показания от исполнителя не отправляли.

Критерий исправления: новая версия импортированного прибора обновляет принадлежащие учёту поля и сохраняет серверное операционное назначение; создание нового прибора без ответственного остаётся допустимым. Нужны целевой тест этого слияния, проверка узких прав сотрудника и реальный повторный импорт перед показом именно этого маршрута. Это отдельный P1 по готовности роли, а не доказательство отказа всего двустороннего обмена.

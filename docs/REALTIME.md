# Автоматическая синхронизация

Один авторизованный кабинет использует одно соединение `WSS /api/realtime`. Сокет передает только список изменившихся ресурсов и курсор `{epoch, revision}`. Записи, персональные данные, суммы и идентификаторы сущностей приходят через обычные HTTP API с актуальной проверкой контекстных прав. JWT передается первым сообщением, никогда в URL. Схема команд и DTO находятся в `packages/contracts/src/realtime*.ts`.

## Фиксация и доставка

Миграция 010 добавляет единственный инфраструктурный checkpoint в `warehouse.realtime_state`. Изменившиеся таблицы определяются существующим SQL diff без повторной загрузки. Бизнес-изменения, аудит, увеличение revision и `pg_notify('wirehouse_changes', ...)` выполняются в одной транзакции. Откат и отсутствие изменений не создают событий. Временные коды входа также не создают событий.

Каждый экземпляр API использует отдельное PostgreSQL LISTEN-соединение; изменения доходят до браузеров других экземпляров без привязки к одному процессу. Сначала устанавливается LISTEN, затем читается checkpoint. Разрыв LISTEN восстанавливается с задержкой и случайным разбросом; восстановление инициирует полную сверку открытых запросов. NOTIFY не является хранилищем событий: пропуски исправляются по сохраненной revision. Прямые SQL-изменения в обход транзакционного API не являются поддерживаемым способом бизнес-записи.

## Ограничение частоты и восстановление

Сервер объединяет события за фиксированное окно 200 мс; клиент объединяет инвалидации еще за 200 мс. Непрерывный поток не откладывает чтение бесконечно. На ключ «сессия + полный URL запроса» работает один HTTP-запрос. События во время чтения вызывают один последующий запрос. Неоткрытые и выгруженные разделы не перечитываются; кешированные данные помечаются устаревшими и сверяются при открытии. Параметры поиска и страницы входят в ключ; устаревшие запросы отменяются.

После каждой готовности сокета открытые запросы перечитываются. Клиент дополнительно проверяет checkpoint по HTTP после подключения и каждые 30 секунд в видимой вкладке, в том числе при недоступности WebSocket. Проверки по сокету также выполняются каждые 30 секунд. Возврат во вкладку/восстановление сети инициирует сверку; раз в минуту выполняется полное чтение для данных, зависящих от текущего времени. Переподключение использует экспоненциальную задержку со случайным разбросом до 30 секунд. Сравнение ревизий выполняется как bigint, смена epoch требует полной сверки.

Временные ошибки HTTP (сеть, 408, 429, 5xx) повторяются с задержкой до 30 секунд. Ошибки 401 завершают сессию, 403/404 убирают старые данные из кеша; постоянные ошибки не повторяются бесконечно. Повтор *обработки пакета обмена* остается отдельной бизнес-командой и не подменяется автоматическим повтором записи.

Черновики форм, поисковые фильтры и страницы таблиц сохраняются при фоновых обновлениях. Условия работы, изменения ППР и планы отправляют версию исходного черновика; новые данные не должны превращать старый черновик в бесконфликтную запись поверх чужих изменений.

## Соединения и эксплуатация

Сервер отправляет ping каждые 25 секунд и закрывает соединение без pong. Входное сообщение ограничено 4 КБ, выходная очередь — 256 КБ; медленный клиент переподключается и сверяется через API. Аутентификация должна завершиться за 5 секунд. Origin сверяется с адресом приложения; для локальной разработки разрешены loopback-origin. Права и блокировка проверяются при входе, проверках, рассылке и heartbeat; подписка не сохраняет прежние привилегии после отзыва доступа. При остановке API закрываются сокеты, heartbeat и LISTEN.

Nginx обслуживает Upgrade только в location `/api/realtime` текущего виртуального хоста, с таймаутом 75 секунд. Директивы и сайты других проектов не меняются. CSP явно разрешает WSS канонического хоста. Проверка обновления: `nginx -t`, подключение WSS на опубликованном адресе, `ready` и последующий `state`; изменение через второй кабинет должно отображаться без перезагрузки страницы.

Проверки: `npm run check`, `TEST_POSTGRES_URL=… npm run test:postgres`, `TEST_POSTGRES_URL=… npm run test:browser`. Тесты покрывают объединение потока, одновременные чтения, отмену и повтор, откат транзакции, независимые экземпляры API, восстановление LISTEN, отзыв доступа, живой комментарий, пропущенное событие при переподключении и сохранение черновика.

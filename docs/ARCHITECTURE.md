# Архитектура

## Web

`App.tsx` — точка сборки `PageBoundary → WorkspaceProvider → WorkspaceRouter`. В нём нет форм, запросов или бизнес-правил. `app/` выбирает авторизацию либо кабинет по роли. `features/` содержит самостоятельные компоненты: договоры, арендаторы, помещения, заявки, биллинг, эксплуатация, импорт и профиль. Страницы кабинета подключаются через `React.lazy`; `Suspense` показывает загрузку, граница ошибок позволяет восстановить страницу.

`useWorkspaceState` хранит состояние сессии и рабочего места. `useWorkspaceView` вычисляет выборки и разрешённые действия. `state/actions/` группирует обработчики по функциям и объявляет типизированные зависимости через `Pick`. `useWorkspaceEffects` отвечает за загрузку, синхронизацию выбранных записей и историю браузера. Это общая модель рабочего места: изменение фильтра пока обновляет подписанные компоненты контекста. Для больших списков следующие шаги — серверная пагинация и разделение контекста по подпискам, а не перенос запросов в отдельные кнопки.

`api/client.ts` — JSON-транспорт, таймауты, отмена запроса и типизированная ошибка. UI отправляет write DTO, а не целую прочитанную запись. Числа преобразуются из полей формы явно; сервер не угадывает типы. Общие DTO ответов находятся в `packages/contracts/src/read-models.ts`.

`features/operations` имеет собственную модель, редактор и карточку записи. Общие кнопки, поля, состояния и токены берутся из `ui/`. CSS старых макетов помещён в слой `legacy`; UI kit находится выше него без борьбы специфичностей. Новый функциональный раздел `Agenda` использует тот же набор компонентов.

## API

`index.js` собирает зависимости, маршруты, HTTP-сервер и планировщик ППР. Маршрут обрабатывает HTTP и права, сервис — предметную операцию, нормализатор — DTO ответа. `http/body.js` проверяет content type, размер, JSON-объект и строгую схему запроса из общего пакета. Ошибки имеют `error`, `code` и при валидации `fields`.

Конфигурация Redis выбирается явно: пустой `REDIS_URL` означает память одного процесса, указанный URL требует доступного Redis. Ошибка подключения не переключает хранилище. Production требует PostgreSQL, уникальный JWT-секрет и запрещает демонстрационные настройки. Некорректные числовые/JSON-параметры и неизвестный драйвер файлов останавливают запуск.

Сотрудник без объекта не получает весь портфель. Контроль сроков доступен только управляющим и администраторам; фильтрация по объектам выполняется на сервере. Решение о продлении хранится отдельно от юридических дат договора, попадает в аудит и обновляется с обязательной версией, чтобы не потерять параллельное изменение.

## Хранение и транзакции

Production использует схему PostgreSQL `warehouse`: 34 предметные таблицы, типизированные колонки, первичные и внешние ключи, уникальные индексы и ограничения сумм/дат. Вложенные документы — чек-листы, распределения и отчёты импорта — остаются отдельными JSONB-полями соответствующей записи. Единого изменяемого JSONB-документа больше нет. `app_state` сохраняется только как защищённый от записи архив перехода.

`persistence/pool.js` создаёт асинхронный пул `pg`. Синхронный запуск `psql` удалён из API. `schema.js` явно сопоставляет поля предметной модели SQL-колонкам; неизвестное поле останавливает сохранение, а не теряется. Версионированный SQL применяется отдельной командой, контрольная сумма миграции проверяется при запуске приложения.

`openDatabase` предоставляет область транзакции на один HTTP-запрос или запуск ППР. `AsyncLocalStorage` изолирует предметную модель каждого запроса. Чтение выполняется в `REPEATABLE READ READ ONLY`; запись получает транзакционную advisory-блокировку, загружает актуальные записи, проверяет бизнес-правила и сохраняет только изменившиеся строки параметризованными SQL-запросами. Нет общего изменяемого кэша между запросами. Блокировка координирует несколько процессов и исключает потерю обновлений, повторную генерацию ППР и одновременное погашение одного кода входа.

`WarehouseDatabase` содержит синхронные предметные операции и локальный откат вложенных операций. В PostgreSQL-режиме это модель внутри уже открытой SQL-транзакции; она не пишет JSON-файлы. JSON остаётся явно выбранным режимом локальной разработки при отсутствии `DATABASE_URL`; production его запрещает.

HTTP-тело принимается до захвата блокировки. Ответ буферизуется до успешного `COMMIT`, включая отложенную проверку внешних ключей. При ошибке SQL клиент получает ошибку вместо ложного подтверждения сохранения. Файловые ответы сейчас также целиком формируются в памяти: потоковых HTTP-маршрутов нет.

OTP, MFA и контекст бота при PostgreSQL и пустом `REDIS_URL` находятся в `auth_challenges`; перезапуск или переход на другой экземпляр API не теряет действующий код. Явно настроенный Redis остаётся обязательным, без автоматического переключения. ППР каждого экземпляра проходит ту же блокировку; уникальный индекс дополнительно запрещает повтор задания на одну дату.

## Пределы масштабирования

Несколько API безопасно работают с одной базой, но бизнес-записи пока сериализованы общей блокировкой. Это выбранный предел текущих связанных предметных операций, а не обещание линейного роста пропускной способности. Читатели не блокируют записи и видят согласованный снимок; каждый запрос пока загружает доступный модели набор таблиц целиком. Следующий этап при росте данных — SQL-репозитории по агрегатам, серверная пагинация и более узкие блокировки с сохранением инвариантов.

Для нескольких контейнеров также нужны общий файловый том на одном хосте либо S3 и балансировщик. Нынешний production compose публикует один API на фиксированном loopback-порту; слепой `--scale api` не является конфигурацией балансировки. Проверки запускают два отдельных процесса на одной базе.

Внешние отправки и файловые операции не участвуют в транзакции PostgreSQL. Физическое удаление файла выполняется только после COMMIT удаления метаданных, чтобы откат SQL не оставил действующий документ без файла. Ошибка очистки логируется и оставляет неиспользуемый файл; при аварийном завершении процесса также может потребоваться очистка сирот. Автоматический повтор всей транзакции отключён, чтобы не повторять эти действия. Для гарантированной доставки нужен transactional outbox и отдельный обработчик; это самостоятельный следующий этап. Инструкции переноса и обратного переключения — [DATABASE.md](DATABASE.md).

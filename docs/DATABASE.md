# PostgreSQL: перенос и эксплуатация

## Модель

Требуется PostgreSQL 16+ с доступным расширением `btree_gist`; первая миграция устанавливает его для ограничения пересекающихся договоров.

Рабочие данные хранятся в 34 таблицах схемы `warehouse`. Простые поля имеют типы `text`, `numeric`, `integer`, `boolean`, `date`, `timestamptz`; вложенные документы имеют тип JSONB. Идентификаторы, деньги, ссылки и даты доступны SQL. Даты без времени не преобразуются через часовой пояс.

Миграция `001-relational.sql` версионируется и проверяется по SHA256. Применённые SQL-файлы не редактируют: новые изменения оформляют следующим файлом и добавляют его в список миграций. `schema_migrations` хранит версии, `storage_control` — режим и исходные количества записей.

## Первый перенос существующей базы

1. Проверить перенос на восстановленной копии, выполнить `npm run check`, `npm run test:postgres` и браузерные сценарии с `TEST_POSTGRES_URL`.
2. Собрать новый образ до остановки сайта.
3. Остановить **все** пишущие экземпляры Wirehouse и планировщики. Сделать согласованный `pg_dump -Fc` и копию файлов. Не трогать соседние приложения.
4. Из нового образа выполнить `node apps/api/src/persistence/cli.js migrate` с `DATABASE_URL` в окружении. В локальной среде — `npm run db:migrate`.
5. Дождаться `status: migrated` либо `already-migrated`. Команда выводит только количества и хеш, без содержимого данных.
6. Запустить новый API, проверить `/health` (`databaseSchema: relational-v1`), вход, чтение и запись. Проверить восстановление нового dump в отдельную базу.

Штатный `update-wirehouse.sh` выполняет шаги 2–6 с резервной копией и защитой отката. Первый шаг выполняется до публикации.

Перенос атомарен: миграционная блокировка → DDL → чтение старого документа → проверка известных полей → INSERT → проверка ограничений → построчное сравнение нормализованных значений → COMMIT. Неизвестная коллекция/поле, дубль или нарушенная связь отменяет перенос. Записи не пропускаются и ссылки не исправляются автоматически. Отсутствующее необязательное поле становится SQL NULL; временные метки приводятся к UTC. Вложенные документы, идентификаторы, пароли, имена хранимых файлов и суммы сохраняются.

`public.app_state` остаётся архивом. Триггер запрещает запись старым API после перехода. Автоматического импорта JSON-файла при пустой PostgreSQL нет. Новую пустую базу миграция создаёт без пользователей; инициализация выполняется отдельно и явно.

## Откат к старому API

Обычная замена образа на версию с `app_state` после миграции недопустима: она увидит архив, а не новые изменения.

1. Остановить все экземпляры API, сохранить резервную копию текущей БД и файлов.
2. **Новым образом** выполнить `node apps/api/src/persistence/cli.js rollback-legacy`.
3. Команда под блокировкой экспортирует актуальные записи в `app_state`, снимает запрет записи архива и переводит `storage_control` в `legacy`. Таблицы сохраняются. Новый API в этом режиме отказывается работать.
4. Только после успешного экспорта запускать старый образ. При повторном переходе `migrate` атомарно перечитает актуальный legacy-документ и снова проверит содержимое таблиц.

После дальнейших миграций обратная совместимость должна проверяться отдельно. Эта процедура описывает именно переход v1 с общего JSONB.

## Проверки и настройки

- `npm run db:status` проверяет миграцию и режим; код возврата ненулевой при несовпадении.
- `DATABASE_POOL_SIZE` — целое 1–50, по умолчанию 8 соединений на процесс. Суммарный лимит всех API и служебных команд должен помещаться в `max_connections` PostgreSQL.
- Подключение ограничено 5 секундами, SQL-запрос — 30 секундами, ожидание блокировки записи — 10 секундами. Занятость возвращает 503; автоматического повтора мутаций нет.
- Для воспроизводимых тестов нужен отдельный PostgreSQL 16+ с правом создания временных баз. Тесты не очищают базу из `TEST_POSTGRES_URL`, а создают и удаляют собственные базы со случайными именами.
- Дамп снимается целиком, включая схему, ограничения и архив перехода. После восстановления выполняйте `db:status` и сверку количеств, а не только чтение `app_state`.

Транзакция использует одно соединение пула, как требует [node-postgres](https://node-postgres.com/features/transactions). Межпроцессная координация использует [транзакционные advisory locks PostgreSQL](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS).

# Обмен Wirehouse 0.3 с Бухгалтерией предприятия

Целевая проверенная конфигурация: **БухгалтерияПредприятия 3.0.208.14, платформа 8.3.27.2214**, файловая база. Установка CFE сохраняет основную конфигурацию поставщика. Совместимость с любой типовой конфигурацией или каждым релизом БП этим не доказана: УТ, УНФ, ERP и отраслевые решения имеют другие метаданные. Перед обновлением другой БП необходим прогон на ее копии.

## Что передается

1С → CRM: объекты, помещения, контрагенты/контакты, договоры, приборы, ЛС и помесячные учетные выписки. CRM → 1С: принятые показания, принятые результаты работ, возвраты результата и акты. Контакты из бухгалтерии не регистрируют пользователей и не выдают права: назначения в CRM остаются явными.

Недвижимость, дополнительные ЛС, приборы и соответствия находятся в собственных регистрах расширения: у типовой БП нет полного справочника эксплуатационной недвижимости. Контрагент и договор связаны с настоящими GUID справочников БП. При выгрузке читаются действительные наименование, ИНН, контактные данные, номер/дата и закрытие договора. Прочие реквизиты портфеля задаются явно.

Выписка читает реальные движения регистра `Хозрасчетный` по организации, договору и настроенным счетам. Начальный остаток + начисления − оплаты должен совпасть с конечным остатком. Неизвестная корреспонденция не превращается в выдуманную оплату: пакет блокируется с диагностикой. Списки доходных/денежных счетов задаются явно, через запятую. Настроенный расчетный счет должен иметь договор во втором субконто; другие аналитики требуют адаптации.

Период настройки — начало истории; агент выгружает месяцы от него до текущего, максимум 120. Детализация выписки ограничена 500 строками. Большой справочник разбивается на пакеты по 500 записей. Версия меняется при изменении содержимого; дата проверки финансов обновляется как минимум раз в сутки. Первичный порядок зависимостей: объект → помещение → контрагент → договор → прибор → ЛС → выписка. Неудачный ранний пакет блокирует последующие до исправления/повтора.

## Установка и подключения

Недостаточно только установить расширение. Нужны источник в CRM, отдельный ключ этого источника, учетная запись БП с необходимыми правами, соответствия и Windows-агент с установленным COMConnector той же разрядности. Для рабочей базы сначала делают резервную копию; обновление файловой базы выполняют монопольно. Пользовательские сеансы принудительно не завершаются.

Секреты — в отдельном приватном env, вне Git. Файловый режим:

```dotenv
ONE_C_CRM_URL=https://your-crm.example
ONE_C_SOURCE_ID=SOURCE-ID-FROM-CRM
ONE_C_ENVIRONMENT=production
ONE_C_SOURCE_TOKEN=PRIVATE-SOURCE-TOKEN
ONE_C_DATABASE=D:/1C/Accounting
ONE_C_USER=integration-user
ONE_C_PASSWORD=PRIVATE-PASSWORD
```

Серверный режим вместо `ONE_C_DATABASE`:

```dotenv
ONE_C_SERVER=one-c.internal:1541
ONE_C_INFOBASE=Accounting
```

Одновременно указывать File и Srvr/Ref нельзя. Windows-агент может находиться на машине с доступом к кластеру; публикация HTTP самой 1С не требуется. Формирование Srvr/Ref проверено тестом; работа с реальным кластером, серверное лицензирование и минимальная роль пользователя отдельно не подтверждены. Это не обещание поддержки любого сервера одной установкой CFE.

Приватный JSON соответствий содержит обязательные `accounts` и `meters`; дополнительные разделы 0.3 — `catalogs` (properties/units/tenants/leases/meters), `finance` (`accountExternalId` + `settings`) и `meterBindings` (`externalId`, `accountExternalId`, `validFrom`). Финансовые settings: `organizationId`, `settlementAccount`, `incomeAccount`, `moneyAccount`, `nomenclatureId`, `period`, `createActs`. Внешние ID контрагента/договора и organizationId/nomenclatureId — реальные GUID выбранной БП. Не сопоставлять клиентов по похожему имени, телефону или общему ИНН автоматически.

```powershell
python scripts/configure-one-c.py --env-file PRIVATE/agent.env --mapping PRIVATE/mapping.json
python integrations/one-c/wirehouse_bridge.py --env-file PRIVATE/agent.env --check
python integrations/one-c/wirehouse_bridge.py --env-file PRIVATE/agent.env
```

Привязку прибора меняют с первого числа месяца. Исторический месяц с принятым показанием менять нельзя. Повтор той же привязки безопасен. Старое показание не переписывается на нового арендатора.

Агент выполняет ограниченный проход и записывает рядом с env безопасный `*.status.json`; токены/пароли туда не попадают. CRM показывает последнее подключение, успешный проход и код ошибки. Периодический watcher текущей установки запускает обмен только при открытом локальном клиенте 1С и сохраняет скрытый запуск без консоли. Для настоящего серверного фонового режима нужно отдельно настроить службу/задание, которое не зависит от открытого клиента.

## Акты и демонстрация

При `createActs=true` акт создает **непроведенный документ `РеализацияТоваровУслуг`** со ссылкой на договор, строками и НДС. Реальная организация использует обычные обработчики БП. Проведение, учетная политика и налоговые регистры требуют бухгалтерской настройки; транспортная квитанция не означает бухгалтерское проведение. При повторе доставки документ не дублируется.

`scripts/one-c-demo.py` вызывается только вручную. `seed` создает явно помеченные `ТЕСТ WH-DEMO-*`: организацию, контрагента, договор, услугу, склад/помещение/прибор/ЛС и настоящие ручные бухгалтерские операции. Это синтетические записи, для которых явно используется режим загрузки. Автоматический агент никогда не создает демонстрационных данных.

Входящий долг 1 000 ₽ + начисление 10 000 ₽ − оплата 6 000 ₽ = долг 5 000 ₽. Тестовый акт 122 ₽ после отдельной помеченной ручной проводки дает 5 122 ₽; исправление исходного начисления до 12 000 ₽ дает 7 122 ₽. Демонстрационная ручная проводка **не проводит реализацию и ее регистры НДС**.

Для рабочей базы `seed`, `post-demo-act`, `correct-charge` требуют флаг `--working-demo` в дополнение к явному действию. Сохраняется манифест GUID, повтор seed не плодит записи и не сбрасывает изменения. Демонстрационные данные нельзя автоматически удалять из бухгалтерии: удаление/сторно выполняет ответственный бухгалтер по манифесту, с сохранением аудита и резервной копии.

```powershell
python scripts/one-c-demo.py test-native --database .local/one-c-build/bp-test --output .local/native-result.json
$env:ONE_C_TEST_DATABASE=(Resolve-Path .local/one-c-build/bp-test).Path
# TEST_POSTGRES_URL — исключительно отдельный тестовый PostgreSQL.
node --test tests/one-c-full-e2e.mjs
```

Нативный тест подтверждает чтение бухгалтерского регистра, порядок семи выгрузок, версии, фактический документ акта, повтор и помесячную смену ЛС. Полный HTTP-тест отдельно подтверждает импорт графа без ручного сопоставления, потерю ack, настоящий процесс сметы/работы/акта, возврат финансов и исправление из БП. Фактические результаты конкретного запуска фиксируются в отчете приемки; наличие тестового файла само по себе не является успешной приемкой.

# WirehouseExchange 0.3.0 · БП 3.0

Текущая версия добавляет выгрузку объектов, помещений, контрагентов, договоров и приборов, автоматические учетные выписки из `Хозрасчетный`, создание документа реализации по акту CRM, помесячную смену ЛС прибора и диагностику последнего обмена. [Установка, настройка и границы версии 0.3](../../docs/ONE_C_0_3_RU.md). Фактическая приемка — [отчет 28.10](../../docs/ACCEPTANCE_2026-10-28.md).

## Архив инструкции 0.2

Следующие сведения описывают предыдущий срез. Для новой установки использовать инструкцию 0.3 выше.

Рабочий интеграционный срез: дополнительные лицевые счета БП → CRM; принятые инженером показания, результаты работ, возвраты и акты CRM → регистры расширения в БП. Проверен на **БухгалтерияПредприятия 3.0.208.14 / 8.3.27.2214**, на синтетических данных отдельной файловой базы. Основная конфигурация поставщика не меняется.

Сквозная проверка использует настоящий справочник договоров БП, API CRM и PostgreSQL. После потери HTTP ack и повторной доставки в 1С остаются одно показание и одна квитанция. Это еще не полный промышленный обмен всех данных ТЗ.

## Модель данных

Расширение добавляет семь независимых регистров:

- `WH_Sources`: источник и неизменяемая среда `test`/`production`.
- `WH_Accounts`: дополнительный ЛС, GUID настоящего договора БП, номер, период, состояние и версия.
- `WH_Meters`: явное соответствие прибора ЛС, начальное значение и доступность.
- `WH_Outbox`: неизменяемый JSON пакета, messageId, попытки, резерв доставки и результат.
- `WH_Readings`: принятые значения, предыдущие значения, прибор, ЛС и расчетный период.
- `WH_Inbox`: messageId, SHA-256 нормализованного содержимого и квитанция, записанная вместе с показанием.
- `WH_WorkEvents`: неизменяемый снимок результата, возврата или акта, внешний ЛС, прикладной ключ события и SHA-256. Версия результата и actId защищены от повторной записи с другим содержимым даже при новом messageId.

Работы/акты сохраняются в одной транзакции с квитанцией. Проверяются настоящий договор БП и ЛС данного источника, версии, обязательные поля; для акта также строки, НДС и сумма. История возврата хранится отдельным событием и не перезаписывает принятый результат. Архив событий допускает доставку в другом порядке; он не изображает текущее состояние заявки. Прием в `WH_WorkEvents` не создает и не проводит `РеализацияТоваровУслуг`: для этого нужен согласованный учетный процесс с организацией, номенклатурой, счетами и ставками НДС.

Добавлена отдельная роль `WH_Integration`: чтение/изменение только собственных регистров. Она не входит в роли по умолчанию. Общий модуль не привилегированный, прямой клиентский серверный вызов выключен. Пользователю агента также необходимы право внешнего соединения и чтение договоров БП через соответствующие штатные роли; проверка минимальной промышленной комбинации ролей еще требуется. Нативные проверки выполнялись с правами администратора тестовой базы.

Настоящий договор проверяется по GUID; удаленный/помеченный договор отклоняется. Для активного ЛС и приема показаний закрытый договор отклоняется. Суммы бухгалтерских документов и проводки этот прототип не изменяет. Запись в `WH_Readings` означает прием показания в 1С; последующий расчет начислений по нему относится к отдельному учетному процессу.

## Подключение

1. Установить релиз CRM с миграцией 011, `GET /api/integrations/accounting/:sourceId/capabilities` и фильтром `kinds` в claim. Старый API без capabilities агент отклонит до доставки.
2. После штатной резервной копии установить CFE через управление расширениями 1С и открыть новую сессию. В этом развертывании 22.10 CFE уже установлен в рабочую БП, SHA-256 конфигурации поставщика до/после совпал.
3. Создать источник учета в CRM с нужной средой; выпущенный Bearer-ключ сохранить в `.local/one-c-agent.env`, используя `agent.env.example`. Не использовать серверный `.env` CRM. Токен не хранится в регистрах 1С и не передается аргументом командной строки.
4. Явно связать договор CRM с GUID договора БП через существующий `/api/accounting/links` (`entityType=leases`, `version=0`). Аналогично связать прибор CRM с выбранным externalId прибора в этом же источнике.
5. Подготовить `.local/one-c-mapping.json` по `mapping.example.json`: заменить все демонстрационные ID/значения реальными. Пример сам по себе не загружается и не является рабочими данными. Указать фактическое начальное показание; сайт и 1С должны использовать одинаковое значение.

Ограничение доступа к приватному env для текущего Windows-пользователя:

```powershell
$agentFile = (Resolve-Path -LiteralPath '.local/one-c-agent.env').Path
$agentUser = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
icacls $agentFile /inheritance:r /grant:r "${agentUser}:(R,W)"
```

Настройка и один проход:

```powershell
python scripts/configure-one-c.py --env-file .local/one-c-agent.env --mapping .local/one-c-mapping.json
python integrations/one-c/wirehouse_bridge.py --env-file .local/one-c-agent.env --check
python integrations/one-c/wirehouse_bridge.py --env-file .local/one-c-agent.env
```

Настройка сохраняется по записи; файл соответствий не объявляется одной транзакцией. При ошибке выгрузка нового пакета не ставится в очередь, уже настроенные соответствия сохраняются. После исправления повторить настройку с теми же ID/версиями. При изменении реквизитов ЛС увеличить версию; перенос существующего ЛС на другой договор запрещен.

Среда CRM, источника и локальной 1С проверяется до получения сообщений. HTTP разрешен только в `test` и только для loopback; production использует HTTPS с проверкой сертификата и запретом редиректов. Вывод агента содержит счетчики и безопасный код ошибки, без URL, ключей, паролей и исходных ответов сервера.

Установка задания после успешного ручного прохода:

```powershell
& integrations/one-c/Register-OneCBridgeTask.ps1 -EnvFile (Resolve-Path .local/one-c-agent.env).Path
```

Это задание работает, пока соответствующий пользователь Windows вошел в систему; окно клиента 1С может быть закрыто. Не утверждается круглосуточная работа после выхода из Windows. Для нее нужен отдельно настроенный сервисный пользователь/служба. В рабочем развертывании задание `Wirehouse-OneC-Exchange` установлено. Агент следует запускать из отдельного каталога проверенного релиза, чтобы правки в рабочем Git-дереве не меняли выполняемый код; env хранится отдельно в `.local/one-c-agent.env` с ограниченным ACL. Пути и результат запуска — в отчете релиза.

## Повторы и отказы

Пакет выгрузки ЛС сохраняется в 1С до HTTP-запроса. При сетевой ошибке он остается с тем же messageId и payload; после истечения 60-секундного резерва доступен повтор. HTTP 200 со `status=failed` не считается успехом. После восьми автоматических попыток требуется устранение причины и явный `RetryOutgoing`; содержимое сообщения не меняется.

Для обратного направления агент согласует `kinds` по capabilities CRM и установленного CFE. Версия 0.2 поддерживает `readings`, `work_results`, `work_reopened`, `service_acts`; со старым CFE агент продолжает запрашивать только `readings`. Неподдержанные типы остаются в CRM. Для каждого показания 1С проверяет источник, ЛС, прибор, период, предыдущее значение, точность и состояние договора. Прикладная запись и квитанция сохраняются в одной транзакции; положительный HTTP ack отправляется после COMMIT. Неопределенный сбой COM оставляет сообщение без ack для безопасного повтора через квитанцию.

Одинаковый messageId с другим содержимым отклоняется. Порядок JSON-ключей не меняет квитанцию. Один submissionId не может содержать разные значения; второй submission для того же прибора/периода также отклоняется. SHA-256 квитанции считается внутри адаптера 1С и не является HMAC/цифровой подписью; транспорт аутентифицируется отдельным Bearer-ключом источника.

## Воспроизведение проверок

Python 3.13.14, `pywin32==312`, 64-битная платформа 1С. Для сборки требуется существующая отдельная база под `.local`; сборщик отказывается работать с произвольной рабочей базой.

```powershell
python scripts/build-one-c.py --database .local/one-c-build/platform-test --platform 'C:/Program Files/1cv8/8.3.27.2214/bin/1cv8.exe'
python scripts/test-one-c-runtime.py --database .local/one-c-build/bp-test --output .local/one-c-build/runtime-bp.json
python -m unittest discover -s tests -p one_c_bridge_test.py -v
$env:ONE_C_TEST_DATABASE = (Resolve-Path .local/one-c-build/bp-test).Path
# TEST_POSTGRES_URL — отдельный тестовый PostgreSQL с правом создавать временные БД.
npm run test:one-c
```

Тестовая БП создана из `.cf` конфигурации исходной БП в пустой файловой базе; клиентские бизнес-данные не копировались. Фикстуры создают настоящие синтетические записи `Контрагенты`/`ДоговорыКонтрагентов` с отключенными прикладными обработчиками загрузки; бухгалтерские документы не проводятся. COM для текущего пользователя Windows восстановлен регистрацией библиотеки типов установленного `comcntr.dll`; машинная регистрация не менялась.

Полная проверка модулей основной БП через `/CheckConfig` не завершалась: первый длительный проход остановлен при смене исходников. Финальный модуль проходит checker на отдельной платформенной базе, а финальный CFE проходит загрузку/обновление на БП и нативные проверки. Это ограничение явно отделено от успешного сквозного теста.

## Следующие части ТЗ

Автоматическая выгрузка контрагентов/контактов, условий договоров, объектов/помещений и приборов из БП; финансовая витрина по согласованной учетной аналитике; бухгалтерское оформление принятых актов; смена ЛС для физического прибора с историей; настройка соответствий через интерфейс 1С; промышленный регламент, права сервисного пользователя, пилот с реальными данными и двумя независимыми базами. Обновление договора БП само по себе пока не формирует новую версию ЛС: требуется обновить соответствие и поставить пакет в очередь.

Read-only инвентаризация рабочей БП 22.10: организации=0, договоры=0, проводки=0, реализации=0, банковские поступления=0; контрагенты=4. Финансовая сверка требует заполненной учетной базы и соответствий организации/договора/аналитики. Повторить срез можно `python scripts/inspect-one-c-data.py --database <путь> --output .local/one-c-data.json`; команда выгружает только количества и метаданные, а не бизнес-записи.
